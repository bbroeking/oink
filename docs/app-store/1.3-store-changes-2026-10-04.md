## Account-deletion repair applied

Frozen source has an account-deletion failure when another profile references
the departing user through `referred_by`. The local PostgreSQL regression
reproduced the FK error, then passed with a narrow `ON DELETE SET NULL` repair:
the inviter was deleted, the referee survived, and its reference was cleared.
The [transaction test record](../../artifacts/release-1.3/account-deletion-transaction-test-results-20261004.md)
passed successful deletion, a changed-boundary abort, and atomic rollback on
history-insert failure using the exact deployment transaction and original RPC.
The repair-specific security contract passed with zero failures.

The pre-repair production schema was **verified through the authenticated
Supabase SQL editor**. `profiles_referred_by_fkey` had `NO ACTION`, and
`delete_my_account()` only deletes the caller's `auth.users` row without
referral cleanup or foreign-key error handling. Its definition MD5 is
`81807648684d60edfc25d55624beef00`. These are the relationships and deletion
statement that failed the local regression. The latest applied migration is
`20260921150000_drum_draw`; four unrelated local pending migrations must be
excluded from this repair. See the [production schema evidence](../../artifacts/release-1.3/account-deletion-production-schema-196.json).

Brian then explicitly authorized: **“Yeah, you can apply the repair.”** The
named migration `20261004201000_account_deletion_referral_cleanup.sql` was
applied through the authenticated SQL editor, with its two constraint
statements and migration-history row in one transaction. A separate read-only
verification passed all six checks: validated `SET NULL` referral constraint,
recorded version, byte-matching statements, all four unrelated migrations still
